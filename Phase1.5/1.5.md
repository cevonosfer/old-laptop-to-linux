
## Configuring SSH Access

To avoid constantly using passwords, I generated SSH keys and stored them in Bitwarden.

I also created an SSH configuration file on my Windows machine so that I could connect using friendly names instead of memorizing IP addresses.

For example, instead of typing:

```
ssh user@192.168.x.x
```

I could simply use:

```
ssh omv
ssh docker
ssh proxmox
```

This made connecting to the servers much more convenient.

## Portainer Access Issue

After deploying Portainer, I initially tried accessing it using:

```
https://localhost:9443
```

The browser returned a connection error, which made me think that Portainer had not started correctly.

After some troubleshooting, I realized that I was opening the address from my Windows machine. In that context, `localhost` referred to my Windows PC, not the Ubuntu VM running Portainer.

The solution was simply to access Portainer using the Ubuntu VM's IP address:

```
https://<ubuntu-vm-ip>:9443
```

Once I did that, Portainer loaded correctly and I was able to complete the setup.

## Creating and Testing Backups

To prepare for future experiments, I began looking into backup strategies.

For Proxmox, I configured VM backups so that both the OMV VM and Ubuntu Docker VM could be restored if I broke something during testing.

For OMV, I created an additional virtual disk specifically for backup testing. Although both virtual disks reside on the same physical drive, the setup allows me to practice backup and restore procedures without needing additional hardware.

I also enabled automatic Portainer backups to preserve configuration, stacks, users, and endpoints.

## SMB Share Access and Troubleshooting

After configuring SMB shares in OMV, I successfully accessed the shared folder from Windows using File Explorer.

Since everything appeared to be working, I decided to map the share as a network drive so it would always be available under a drive letter.

However, Windows refused to map the drive and displayed the following error:

```text id="4h0bn0"
Multiple connections to a server or shared resource by the same user,
using more than one user name, are not allowed.
```

At first this was confusing because I could already browse the share manually.

After investigating further, I discovered that Windows had already established an SMB connection to the OMV server using a different set of credentials. Windows does not allow multiple active SMB sessions to the same server using different usernames.

To verify this, I listed the active network connections:

```
net use
```

The existing SMB sessions confirmed that Windows was already connected to the server.

And then i went to the Credential Manager and deleted all the connection associated with the omv.

After removing the existing SMB sessions, I attempted to map the network drive again.

This time the mapping completed successfully and the share appeared as a normal drive in Windows.
